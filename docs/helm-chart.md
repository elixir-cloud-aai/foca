# Helm library chart

FOCA provides a [library chart][library-charts], `foca-common`, for deploying
FOCA apps on Kubernetes (and OpenShift) with [Helm](https://helm.sh/). It
implements the setup described in [Kubernetes and
Helm](deployment.md#kubernetes-and-helm), so that each app only needs a thin
chart: its values, a few settings and one line per resource. It renders:

- the app's `Deployment` (non-root security contexts, read-only root file
  system with a writable `/tmp`, probes, a `preStop` delay,
  `enableServiceLinks: false`, optional [Gunicorn](https://gunicorn.org/)
  settings);
- a `ConfigMap` with the config overlay, rendered from the `config` value and
  mounted via `FOCA_CONFIG_OVERLAY`; the pods are rolled when it changes;
- the app's `Service`, and a Gateway API `HTTPRoute` (optionally with a
  redirect from HTTP to HTTPS), an `Ingress` (optionally with a cert-manager
  certificate) or, on OpenShift, a `Route` (see [Exposing the
  app](#exposing-the-app));
- `NetworkPolicy`s for the app (opt-in) and MongoDB;
- an optional MongoDB (`Deployment`, `Service`, `PersistentVolumeClaim`, and
  an init script that creates the app user), with credentials from an
  existing `Secret`; external databases work too;
- an optional [Celery](https://docs.celeryq.dev/) worker (`Deployment` with
  the app's image) for [background tasks](configuration/jobs.md), and an
  optional [RabbitMQ](https://www.rabbitmq.com/) broker (`StatefulSet`,
  `Service`, `NetworkPolicy`, `PersistentVolumeClaim`, and a `ConfigMap`
  with its config), with the broker URL from an existing `Secret`; external
  brokers work too.

The library chart lives in [`charts/foca-common`][library] and is versioned
independently of FOCA. The [petstore example][petstore-chart] has a thin chart
built on it, which you can copy as a starting point. Its image is not
published; it serves the app with Gunicorn. To try the example, build it and
the FOCA image it is based on, and load it into the cluster (e.g., for
[kind](https://kind.sigs.k8s.io/)):

```bash
cd examples/petstore
docker compose build foca-petstore-root
docker build -t foca-petstore .
kind load docker-image foca-petstore
```

## Building an app chart

An app chart depends on the library chart in its `Chart.yaml`:

```yaml title="Chart.yaml"
apiVersion: v2
name: my-app
description: My FOCA app
type: application
version: 0.1.0
appVersion: "1.0.0"
dependencies:
  - name: foca-common
    version: 0.2.0
    repository: oci://ghcr.io/elixir-cloud-aai/charts
```

The library chart's [releases](#releases) are published to this OCI
repository; to work on the library chart itself, use a `file://` repository
in a clone of FOCA, as the petstore example does. Run `helm dependency
update` to download it (into `charts/`, which you may add to `.gitignore`)
and to create `Chart.lock`, which you commit.

### Settings

The library's templates need a few settings of the app that are not values,
as they are fixed by the app's image. Define them in a named template of the
app chart, as YAML:

```yaml title="templates/_helpers.tpl"
{{- define "my-app.settings" -}}
valuesKey: myApp
mongodb:
  databases: [myAppStore]
{{- end -}}
```

| Setting | Description |
| --- | --- |
| `valuesKey` | Required: key of the app's values (see [Values](#values)), e.g., `myApp` for an app `my-app` (camelCase, following Helm's conventions). |
| `containerName` | Name of the app's container; by default the chart name. |
| `configDir` | Directory where the config overlay is mounted (as `overlay.yaml`); by default `/etc/<chart name>`. |
| `config` | Config generated by the chart (e.g., from other values), merged into the overlay before the `config` value, which takes precedence. |
| `maxContentLength` | Size limit of request bodies of the app's base config (`server.max_content_length`), in bytes, if it sets one. The helper `foca-common.maxContentLength` returns it, unless `config.server.max_content_length` overrides it, e.g., for a size limit at the proxy in resources of the app chart's own; the library's resources don't use it (see [Exposing the app](#exposing-the-app)). |
| `requireAudience` | If `true`, rendering fails without an audience for tokens (`config.security.auth.audience`), unless audience validation is disabled; set it if the app's base config has token issuers. |
| `mongodb.databases` | Databases of the app's base config (`db.dbs`); the first one is the one FOCA authenticates against. Required for the bundled MongoDB with authentication, whose init script creates the app user with access to them. |
| `mongodb.accessControlDatabase` | Database of [access control](access-control.md) (`security.access_control.db_name`, by default `access_control_db`), if the app's base config enables it; the init script of the bundled MongoDB also gives the app user access to it (see the [deployment notes](#deployment-notes)). |

For example, an app that advertises its public URL in its config can
generate it from the `hostName` value:

```yaml title="templates/_helpers.tpl"
{{- define "my-app.settings" -}}
valuesKey: myApp
maxContentLength: 1048576
requireAudience: true
mongodb:
  databases: [myAppStore]
config:
  custom:
    public_url: {{ printf "https://%s/" (required "hostName must be set" .Values.hostName) | quote }}
{{- end -}}
```

### Templates

Each template of the library renders one resource (or nothing, if it is
disabled by the values). Call them with a dict of the root context (`root`)
and the settings (`settings`), one per file:

```yaml title="templates/deployment.yaml"
{{- include "foca-common.deployment" (dict "root" . "settings" (include "my-app.settings" . | fromYaml)) }}
```

| Template | Renders |
| --- | --- |
| `foca-common.configMap` | `ConfigMap` with the config overlay; also checks the values, so every app chart must include it |
| `foca-common.deployment` | the app's `Deployment` |
| `foca-common.service` | the app's `Service` (port 8080) |
| `foca-common.ingress` | `Ingress`, if `<valuesKey>.ingress.enabled` |
| `foca-common.httpRoute` | Gateway API `HTTPRoute`, if `<valuesKey>.httpRoute.enabled` |
| `foca-common.httpsRedirectRoute` | `HTTPRoute` redirecting HTTP to HTTPS, if `<valuesKey>.httpRoute.enabled` and `<valuesKey>.httpRoute.httpsRedirect.enabled` |
| `foca-common.route` | OpenShift `Route`, unless `<valuesKey>.route.enabled` is false, without an Ingress or HTTPRoute, if the cluster serves `route.openshift.io/v1` |
| `foca-common.networkPolicy` | the app's `NetworkPolicy`, if `<valuesKey>.networkPolicy.enabled` |
| `foca-common.mongodbDeployment` | MongoDB's `Deployment`, unless `mongodb.enabled` is false |
| `foca-common.mongodbInitScript` | `ConfigMap` with MongoDB's init script, if `mongodb.auth.enabled` |
| `foca-common.mongodbNetworkPolicy` | MongoDB's `NetworkPolicy`, if `mongodb.networkPolicy.enabled` |
| `foca-common.mongodbPersistentVolumeClaim` | MongoDB's data volume, unless `mongodb.enabled` or `mongodb.persistence.enabled` is false (both true if not set), without `mongodb.persistence.existingClaim`; kept on uninstallation unless `mongodb.persistence.resourcePolicy` is empty |
| `foca-common.mongodbService` | MongoDB's `Service` (port 27017), the host of `db.host` in the overlay |
| `foca-common.workerDeployment` | the Celery worker's `Deployment`, if `worker.enabled` |
| `foca-common.brokerStatefulSet` | the broker's (RabbitMQ's) `StatefulSet`, if `broker.enabled` (`foca-common.brokerDeployment`, the name up to 0.1.0, is a deprecated alias) |
| `foca-common.brokerConfigMap` | `ConfigMap` with the broker's config file, if `broker.enabled` |
| `foca-common.brokerNetworkPolicy` | the broker's `NetworkPolicy`, if `broker.enabled` and `broker.networkPolicy.enabled` |
| `foca-common.brokerPersistentVolumeClaim` | the broker's data volume, if `broker.enabled` and `broker.persistence.enabled`, without `broker.persistence.existingClaim` |
| `foca-common.brokerService` | the broker's `Service` (port 5672), the host of the broker URL |

App charts without background tasks may leave out the worker's and broker's
templates and values.

Helpers such as `foca-common.fullname`, `foca-common.labels` and
`foca-common.routeEnabled` are available for the app's own resources and
`templates/NOTES.txt` (see the petstore example). App charts may add further
resources and checks, e.g., a template that fails on values the app does
not support any more, included before the ConfigMap:

```yaml title="templates/configmap.yaml"
{{- include "my-app.validate" . -}}
{{- include "foca-common.configMap" (dict "root" . "settings" (include "my-app.settings" . | fromYaml)) }}
```

### Values

The library chart has no values of its own: its templates read those of the
app chart, which must contain all of them with their defaults (Helm does not
pass a library's values to the charts that include it). Copy `values.yaml`
of the [petstore example][petstore-chart] and rename the key `petstore` to
your app's `valuesKey`:

| Values | Description |
| --- | --- |
| `nameOverride`, `fullnameOverride` | Resource names: `<release>-<chart>` (or `<release>` if it contains the chart name) for the app, the same with the suffixes `-mongodb`, `-worker` and `-broker` for MongoDB, the worker and the broker |
| `hostName` | Public host name of the Ingress, HTTPRoute or Route |
| `config` | Config overlay, merged by FOCA into the base config in the image |
| `<valuesKey>` | The app's container: `image` and `tag` (by default the chart's `appVersion`), `imagePullPolicy`, `probePath`, `ingress`, `httpRoute`, `route`, `networkPolicy`, `podSecurityContext`, `securityContext`, `resources`, `tmpSizeLimit`, `preStopSleepSeconds`, `gunicorn` |
| `mongodb` | MongoDB: `enabled`, `image`, `imagePullPolicy`, `auth`, `networkPolicy`, `persistence` (`volumeSize`, its size up to 0.1.0, is a deprecated alias of `persistence.size`), `podSecurityContext`, `securityContext`, `resources`, `tmpSizeLimit` |
| `worker` | Optional Celery worker: `enabled` (false if not set), `command`, `replicas`, `readinessProbe`, `livenessProbe` (none by default), `terminationGracePeriodSeconds`, `resources`, `tmpSizeLimit` |
| `broker` | Optional broker: `enabled` (the bundled RabbitMQ; false if not set), `existingSecret`, `image`, `imagePullPolicy`, `networkPolicy`, `podSecurityContext`, `securityContext`, `resources`, `persistence`, `dataSizeLimit`, `tmpSizeLimit` |

The values are described in detail in the example's `values.yaml`.

The `config` value is the config overlay: FOCA merges it into the base
config of the app's image (see [Deployment](deployment.md#kubernetes-and-helm)),
so [named entries](configuration/index.md#named-entries) of `api.specs` and
`security.access_control.policies` can be changed one at a time, by name,
also across several values files (`-f`), which Helm merges like FOCA does.
Removals work differently, though: `null` removes an entry of the app's base
config, but to remove an entry that another values file adds, delete it from
that values file. A `null` for it reaches FOCA, as the chart has no default
for it, and FOCA refuses to start, as the base config has no such entry.

The chart mounts only the config overlay, not other files, so give [spec
patches](configuration/api.md#patching-specifications) inline, as mappings
in `patches`:

```yaml title="values-prod.yaml"
config:
  api:
    specs:
      my-api:
        patches:
          - info:
              description: Deployment of My App at Example Org
```

The library's schema of these values is
[`app-values.schema.json`][library]: copy it to the app chart as
`values.schema.json` and add the app's key, e.g., `"myApp": {"$ref":
"#/$defs/app"}`, so that Helm validates the values.

## Exposing the app

The chart exposes the app for `hostName` in one of three ways:

- a [Gateway API](https://gateway-api.sigs.k8s.io/) `HTTPRoute`
  (`<valuesKey>.httpRoute`), attached to an existing Gateway; recommended for
  new clusters;
- an `Ingress` (`<valuesKey>.ingress`, enabled by default), for an ingress
  controller;
- an OpenShift `Route` (`<valuesKey>.route`), if neither is enabled and
  the cluster serves `route.openshift.io/v1`.

The chart has no defaults for a particular ingress controller or Gateway
implementation: their annotations, policies and NetworkPolicy peers go into
the values (or next to the release), with examples for common setups below.

The Ingress and the HTTPRoute are mutually exclusive: rendering fails if
both are enabled, so set `<valuesKey>.ingress.enabled: false` to use the
HTTPRoute. To expose the app with resources outside the release (e.g., an
HTTPRoute or Ingress that routes only some paths), disable the Ingress and,
for OpenShift, the Route (`<valuesKey>.route.enabled: false`). App charts
built on an earlier version of the library add the templates
`foca-common.httpRoute` and `foca-common.httpsRedirectRoute` (see
[Templates](#templates)) and the `httpRoute` and `route` values of the
petstore example.

Whichever way the app is exposed, check these settings, described for each
setup below:

- **TLS and HTTPS redirect:** clients send bearer tokens, so serve the app
  over HTTPS only (see the [deployment notes](#deployment-notes)).
- **Body size:** the app's own limit, `config.server.max_content_length`
  (by default the setting `maxContentLength` of the app chart; see
  [server](configuration/server.md)), is enforced by FOCA in every setup.
  A limit at the proxy is an extra layer that rejects large requests before
  they reach the app; its configuration depends on the proxy, so the chart
  sets none (see the examples below; keep it at or above the app's limit).
- **Rate limiting:** configured at the proxy only, if at all.
- **NetworkPolicy peers:** `<valuesKey>.networkPolicy.ingressFrom` must
  match the pods of the proxy that forwards requests to the app; NetworkPolicy
  peers select pods by labels and namespaces, or IP ranges (`ipBlock`).
  There are no default peers (see [NetworkPolicy
  peers](#networkpolicy-peers)).
- **Keep-alive:** Gunicorn closes idle connections after
  `<valuesKey>.gunicorn.keepalive` seconds (75 by default). Keep this longer
  than the proxy's idle timeout of connections to the app, as the proxy might
  otherwise send a request on a connection that Gunicorn closes at the same
  time, which fails with `502` or `503`.

### Gateway API

The Gateway API is the successor of the Ingress API. A cluster runs one of
its [implementations](https://gateway-api.sigs.k8s.io/implementations/)
(e.g., [Envoy Gateway](https://gateway.envoyproxy.io/),
[Istio](https://istio.io/), [NGINX Gateway
Fabric](https://docs.nginx.com/nginx-gateway-fabric/),
[Traefik](https://traefik.io/), [Cilium](https://cilium.io/), or a cloud
provider's), and its operators provide a Gateway with listeners for HTTP and
HTTPS, which hold the TLS certificates. The app chart attaches an HTTPRoute
(named like the app) to the Gateway's HTTPS listener via `parentRefs`, and,
with `httpsRedirect`, a second HTTPRoute (`<app name>-https-redirect`) that
redirects HTTP to HTTPS (`301`) to its HTTP listener:

```yaml title="values-prod.yaml"
myApp:
  ingress:
    enabled: false
  httpRoute:
    enabled: true
    parentRefs:
    - name: gateway
      namespace: gateway-system
      sectionName: https
    httpsRedirect:
      enabled: true
      parentRefs:
      - name: gateway
        namespace: gateway-system
        sectionName: http
```

- **TLS:** terminated at the Gateway's HTTPS listener, with a certificate
  of the Gateway's operators, e.g., from
  [cert-manager](https://cert-manager.io/docs/usage/gateway/) via an
  annotation of the Gateway. Its listeners must admit routes from the app's
  namespace (`allowedRoutes`). To bring the app's own certificate to a
  shared Gateway, attach the HTTPRoute to a `ListenerSet` (`kind:
  ListenerSet` in `parentRefs`; Gateway API 1.5 or later), if the
  implementation supports it.
- **HTTPS redirect:** without `sectionName` (or `port`), a parent reference
  attaches the route to all listeners of the Gateway, so set it in both
  `parentRefs` and `httpsRedirect.parentRefs` (`sectionName` in both, or
  `port` in both); rendering fails if they may attach to the same listener,
  which would redirect HTTPS requests, too. The redirect's HTTPRoute has no
  annotations.
- **Body size and rate limiting:** the Gateway API has no standard
  settings for them; implementations offer policies that attach to the
  HTTPRoute or the Gateway (created next to the release, as they are
  implementation-specific), or filters that the HTTPRoute refers to
  (`httpRoute.filters`, e.g., an `ExtensionRef`). For example, for Envoy
  Gateway (with the app `my-app` installed as release `my-app`), a
  `BackendTrafficPolicy` that buffers requests up to 1 MiB (`413` above;
  buffering doesn't suit streamed requests), allows 100 requests per second
  per Envoy proxy and closes idle connections to the app after 60 seconds
  (by default after 1 hour):

    ```yaml
    apiVersion: gateway.envoyproxy.io/v1alpha1
    kind: BackendTrafficPolicy
    metadata:
      name: my-app
    spec:
      targetRefs:
      - group: gateway.networking.k8s.io
        kind: HTTPRoute
        name: my-app
      requestBuffer:
        limit: 1Mi
      rateLimit:
        local:
          rules:
          - limit:
              requests: 100
              unit: Second
      timeout:
        http:
          connectionIdleTimeout: 60s
    ```

    NGINX Gateway Fabric limits body sizes with a `ClientSettingsPolicy`
    (`body.maxSize`); for Traefik, see [Traefik](#traefik).
- **NetworkPolicy peers:** the implementation's proxies (data plane), which
  run in the Gateway's namespace (e.g., Istio, NGINX Gateway Fabric) or in
  that of the implementation (e.g., Envoy Gateway's default deployment
  mode; see [NetworkPolicy peers](#networkpolicy-peers)).

The CI of FOCA installs the petstore example with an HTTPRoute on Envoy
Gateway (`ci/gateway-values.yaml`).

### ingress-nginx

[ingress-nginx](https://kubernetes.github.io/ingress-nginx/) is
[retired](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/):
it gets no releases or security fixes after March 2026. The chart's
Ingress works with it, with the annotations below, but plan the migration to
the Gateway API, or to another ingress controller.

- **TLS:** `<valuesKey>.ingress.https` requests a certificate from
  cert-manager for the Ingress; ingress-nginx then redirects HTTP to HTTPS.
  If TLS is terminated in front of the cluster, set the annotation
  `nginx.ingress.kubernetes.io/force-ssl-redirect: "true"` in
  `<valuesKey>.ingress.annotations` (ingress-nginx must trust the
  `X-Forwarded-Proto` header of the proxy in front, via
  `use-forwarded-headers` in its ConfigMap, or it redirects in a loop).
- **Body size:** ingress-nginx limits request bodies to 1 MiB by default;
  set its limit with an annotation, e.g., to 8 MiB for an app with
  `config.server.max_content_length: 8388608`:

    ```yaml
    myApp:
      ingress:
        annotations:
          nginx.ingress.kubernetes.io/proxy-body-size: 8m
    ```

    Before foca-common 0.2.0, the chart set this annotation to the app's
    limit itself.
- **Rate limiting:** annotations, e.g., per client IP address
  `nginx.ingress.kubernetes.io/limit-rps: "10"`,
  `nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"` and
  `nginx.ingress.kubernetes.io/limit-connections: "20"` (excess requests get
  `503`); behind a load balancer, ingress-nginx must see the clients'
  addresses (e.g., `use-forwarded-headers` or the PROXY protocol).
- **NetworkPolicy peers:** the controller's pods in the namespace
  `ingress-nginx` (see [NetworkPolicy peers](#networkpolicy-peers)).
- **Keep-alive:** ingress-nginx closes idle connections to the app after 60
  seconds (`upstream-keepalive-timeout`).

To migrate an app to the Gateway API, replace the Ingress values with the
HTTPRoute values above and move its annotations to the implementation's
policies; [ingress2gateway](https://github.com/kubernetes-sigs/ingress2gateway)
converts Ingresses (including many ingress-nginx annotations) to Gateway API
resources, which helps to translate them. The Gateway usually has another
address than the ingress controller, and one release cannot have both an
Ingress and an HTTPRoute. To switch without downtime:

1. If the app's NetworkPolicy is enabled, add the Gateway's peers to
   `<valuesKey>.networkPolicy.ingressFrom` and upgrade the release.
2. Create an HTTPRoute by hand, e.g., rendered with `helm template` and the
   new values, under another name.
3. Switch the DNS records of `hostName` to the Gateway.
4. Upgrade the release to the HTTPRoute, removing the ingress controller's
   peers from `ingressFrom`, and delete the HTTPRoute created by hand.

### Traefik

[Traefik](https://doc.traefik.io/traefik/) (e.g., the default ingress
controller of [k3s](https://k3s.io/)) serves Ingresses and the Gateway API.
For an Ingress, set `<valuesKey>.ingress.className: traefik` (unless it is
the default class), and Traefik's annotations in
`<valuesKey>.ingress.annotations`.

- **TLS:** `<valuesKey>.ingress.https` requests a certificate from
  cert-manager for the Ingress; redirect HTTP to HTTPS on Traefik's HTTP
  entry point (static configuration,
  `entryPoints.web.http.redirections.entryPoint.to: websecure`), or serve
  the Ingress on the HTTPS entry point only (annotation
  `traefik.ingress.kubernetes.io/router.entrypoints: websecure`).
- **Body size and rate limiting:** `Middleware` resources
  (`traefik.io/v1alpha1`, created next to the release) with
  `buffering.maxRequestBodyBytes` and `rateLimit`; an Ingress refers to them with the annotation
  `traefik.ingress.kubernetes.io/router.middlewares:
  <namespace>-<middleware>@kubernetescrd`, an HTTPRoute with a filter:

    ```yaml
    httpRoute:
      filters:
      - type: ExtensionRef
        extensionRef:
          group: traefik.io
          kind: Middleware
          name: my-app-limits
    ```

- **NetworkPolicy peers:** Traefik's pods, e.g., in the namespace
  `kube-system` on k3s (see [NetworkPolicy peers](#networkpolicy-peers)).
- **Keep-alive:** Traefik closes idle connections to the app after 90
  seconds (`forwardingTimeouts.idleConnTimeout` of its servers transport),
  later than Gunicorn by default: raise `<valuesKey>.gunicorn.keepalive`
  (e.g., to 100), or lower Traefik's timeout.

### OpenShift

Without an Ingress and an HTTPRoute (`<valuesKey>.ingress.enabled: false`),
the chart creates a Route for all paths on clusters that serve
`route.openshift.io/v1`, unless `<valuesKey>.route.enabled` is false (e.g.,
for a Route of your own that serves only some paths). Recent OpenShift
releases also offer the Gateway API (see [Gateway API](#gateway-api)).

- **TLS:** the router terminates TLS (edge termination, by default with its
  wildcard certificate) and redirects HTTP to HTTPS.
- **Body size:** the router has no limit for request bodies; the app's own
  limit applies.
- **Rate limiting:** annotations of the router in
  `<valuesKey>.route.annotations`, e.g.,
  `haproxy.router.openshift.io/rate-limit-connections: "true"` with
  `haproxy.router.openshift.io/rate-limit-connections.rate-http: "100"`.
- **NetworkPolicy peers:** the router's namespaces (see [NetworkPolicy
  peers](#networkpolicy-peers)).

### Cloud load balancers

Managed Kubernetes services connect Gateways or Ingresses to their load
balancers, e.g., the [GKE Gateway
controller](https://cloud.google.com/kubernetes-engine/docs/concepts/gateway-api),
the [AWS Load Balancer
Controller](https://kubernetes-sigs.github.io/aws-load-balancer-controller/)
and [Application Gateway for
Containers](https://learn.microsoft.com/azure/application-gateway/for-containers/)
on Azure. Use the HTTPRoute values with the provider's Gateway (or
`<valuesKey>.ingress.className` and its annotations for an Ingress), and
the provider's documentation for certificates, HTTPS redirects, body size
and rate limits (often part of its web application firewall). Load
balancers that send requests to the pods directly (container-native load
balancing) connect from the provider's IP ranges, which the NetworkPolicy
must admit with `ipBlock` peers; check the provider's documentation for
them (e.g., its health check ranges).

### NetworkPolicy peers

The app's NetworkPolicy (`<valuesKey>.networkPolicy.enabled`, disabled by
default) admits only the peers in `<valuesKey>.networkPolicy.ingressFrom`,
on the app's port, and the kubelet's probes. There are no default peers, as
they depend on the cluster: set them to the pods of the cluster's ingress
controller (or the OpenShift router, or the Gateway's proxies) when enabling
the policy; otherwise, the app is unreachable through them. Rendering fails
if the policy is enabled without peers (which would allow all sources).
NetworkPolicies only take effect if the cluster's network plugin enforces
them (e.g., Calico or Cilium), and they add up: a pod that several policies
select accepts the connections that any of them allows.

Namespaces are selected by their label `kubernetes.io/metadata.name` (set
on all namespaces from Kubernetes 1.21). Pick the peers of your setup, and
add any other clients in the cluster that call the app's Service directly,
e.g.:

```yaml title="values-prod.yaml"
myApp:
  networkPolicy:
    enabled: true
    ingressFrom:
    # Envoy Gateway (Gateway API, default deployment mode): the proxies of
    # the Gateway `gateway` in the namespace `gateway-system`, which run in
    # the controller's namespace `envoy-gateway-system` (in the Gateway
    # namespace mode, select the Gateway's namespace instead)
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: envoy-gateway-system
      podSelector:
        matchLabels:
          gateway.envoyproxy.io/owning-gateway-namespace: gateway-system
          gateway.envoyproxy.io/owning-gateway-name: gateway
    # Traefik, e.g., on k3s: its pods in the namespace `kube-system`
    # - namespaceSelector:
    #     matchLabels:
    #       kubernetes.io/metadata.name: kube-system
    #   podSelector:
    #     matchLabels:
    #       app.kubernetes.io/name: traefik
    # ingress-nginx (retired): its pods in the namespace `ingress-nginx`
    # - namespaceSelector:
    #     matchLabels:
    #       kubernetes.io/metadata.name: ingress-nginx
    #   podSelector:
    #     matchLabels:
    #       app.kubernetes.io/name: ingress-nginx
    # OpenShift: the router's namespaces
    # - namespaceSelector:
    #     matchLabels:
    #       policy-group.network.openshift.io/ingress: ""
    # Implementations that deploy a Gateway's proxies in its namespace
    # (e.g., Istio): the pods with the Gateway API's label of the Gateway
    # - namespaceSelector:
    #     matchLabels:
    #       kubernetes.io/metadata.name: gateway-system
    #   podSelector:
    #     matchLabels:
    #       gateway.networking.k8s.io/gateway-name: gateway
    # A client in the release's namespace
    - podSelector:
        matchLabels:
          app.kubernetes.io/name: my-portal
```

The list is not exhaustive: for other ingress controllers and Gateway
implementations (e.g., NGINX Gateway Fabric, which also runs its proxies in
the Gateway's namespace), check the namespace and the labels of their proxy
pods in their documentation (or with `kubectl get pods -A --show-labels`);
for cloud load balancers, see [Cloud load balancers](#cloud-load-balancers).

## Deployment notes

- **MongoDB credentials** come from an existing Secret
  (`mongodb.auth.existingSecret`) with the keys `username` and `password`
  (the app user, passed to the app as `MONGO_USERNAME` and `MONGO_PASSWORD`),
  and `root-username` and `root-password` (the root user of the bundled
  MongoDB). The init script creates the app user only when MongoDB starts
  with an empty data directory (and not if that first start is interrupted
  before it ran): to change the app user's password, to give it access to
  further databases, or to create it for an existing database, use `mongosh`
  as the root user, and roll the app's pods after changing the Secret. Authentication can be disabled with
  `mongodb.auth.enabled: false`, but then any pod that can reach MongoDB can
  read and modify its data.
- **MongoDB data** is kept in a PersistentVolumeClaim named like the app
  with the suffix `-mongodb`, mounted at `/data/db` (`mongodb.persistence`:
  `size`, `accessModes`, by default `ReadWriteOnce`, and `storageClass`,
  the cluster's default class if empty and `-` for no dynamic
  provisioning), or in an `existingClaim`, e.g., one restored from a
  backup. MongoDB's Deployment starts a new pod only once the old one is
  gone (`Recreate`). Persistence is enabled also if
  `mongodb.persistence.enabled` is not set (as in values written for
  foca-common 0.1.0). With `mongodb.persistence.enabled: false` (e.g., for
  tests), the data is kept in an `emptyDir` (limited to
  `mongodb.persistence.size`, if set) and lost when the pod is replaced, and
  the init script runs on every new pod.

    Helm keeps the claim, and with it the database, when the release is
    uninstalled, and when the claim is removed from the release by
    disabling persistence or switching to an `existingClaim`: the claim is
    annotated with `helm.sh/resource-policy: keep`
    (`mongodb.persistence.resourcePolicy: keep`, also if not set). To remove
    the data, delete the claim by hand after uninstalling the release
    (`kubectl delete pvc my-app-mongodb`).

    A new release of the same name in the same namespace adopts the kept
    claim, with its data and the app user (the init script does not run
    again). A release with other resource names (another release name,
    without `fullnameOverride`) gets a new claim, i.e., an empty database,
    while one of another release name with the same resource names fails
    on the kept claim; to use the kept data in such a release, set the kept
    claim as its `existingClaim`.

    On upgrades, Helm checks the annotation on the claim in the cluster, so
    the claim of a release installed with foca-common 0.1.0 (or with an
    empty `resourcePolicy`) is annotated only by the next upgrade: disable
    persistence or switch to an `existingClaim` in a later upgrade, or
    annotate the claim first (`kubectl annotate pvc my-app-mongodb
    helm.sh/resource-policy=keep`). Likewise, an upgrade that empties
    `resourcePolicy` removes the annotation, and Helm deletes the claim
    (and, with the usual reclaim policy `Delete`, the data) with the release
    or when a later upgrade removes it from the release (not in the same
    upgrade). A rollback to a revision without the annotation (e.g., one of
    foca-common 0.1.0) removes it from the claim, too; annotate the claim
    again before uninstalling such a release. The broker's claim is not
    kept by default, as its queue can be rebuilt
    (`broker.persistence.resourcePolicy`).

    `mongodb.volumeSize`, the setting up to foca-common 0.1.0, is
    deprecated since 0.2.0 but still sets the claim's size; the claim keeps
    its name, so upgrades keep the data. Rendering fails if
    `mongodb.persistence.size` is set, too, as one of them would be
    ignored: move the size to `mongodb.persistence.size`, and if the app
    chart's values still set `volumeSize`, unset it with `null` (e.g.,
    `--set-json mongodb.volumeSize=null`).
- **Access control:** FOCA keeps the rules of [access
  control](access-control.md) in a database of their own
  (`security.access_control.db_name`, by default `access_control_db`),
  which the app user needs access to, or the app fails at startup (`not
  authorized on access_control_db`). The init script of the bundled MongoDB
  grants it, in this order of precedence: `db_name` of the config overlay
  (`config.security.access_control.db_name`); the setting
  `mongodb.accessControlDatabase`, which app charts set if the app's base
  config enables access control; FOCA's default database, if the overlay
  enables access control (`config.security.access_control.enabled`). A
  `db_name` or the setting is granted even if the overlay disables access
  control. If `db_name` is one of the app's databases, the rules are kept
  there. Database names (also those of `mongodb.databases`) must be shorter
  than 64 characters, all printable ASCII except `/\. "$*<>:|?` and single
  quotes, or rendering fails. For existing databases (the init script has
  run) and external databases, grant the app user `readWrite` on that
  database with `mongosh`.
- **HTTPS:** clients send bearer tokens with their requests, so serve the
  app over HTTPS only (see [Exposing the app](#exposing-the-app) for each
  setup). An HTTPRoute is served with the TLS certificates of the Gateway's
  listeners. The Ingress serves plain HTTP unless
  `<valuesKey>.ingress.https.enabled` requests a certificate from
  cert-manager (via the ClusterIssuer `<valuesKey>.ingress.https.issuer`);
  otherwise, terminate TLS in front of the cluster (e.g., at a load
  balancer), or set a TLS certificate of the ingress controller and redirect
  HTTP to HTTPS via `<valuesKey>.ingress.annotations`. OpenShift Routes use
  edge TLS termination and redirect HTTP to HTTPS. The petstore example
  warns in its `NOTES.txt` if the Ingress has no TLS; app charts should do
  the same.
- **External databases:** with `mongodb.enabled: false`, no MongoDB is
  deployed; set its host (and port) in `config.db` (rendering fails without
  `config.db.host`), and the credentials of the app user via
  `mongodb.auth.existingSecret` (or disable `mongodb.auth.enabled`). The
  app's values keep the `mongodb` map for these settings.
- **Celery worker and broker:** for apps with [background
  tasks](configuration/jobs.md), `worker.enabled` deploys a worker with the
  app's image, run with `worker.command` (e.g., `["celery", "--app",
  "my_app.worker:celery_app", "worker"]`, with the app's worker entry point;
  the petstore example has one, `worker.py`), and with the app's config
  overlay, MongoDB credentials and security contexts. `broker.enabled`
  deploys RabbitMQ as the broker. Both need an existing Secret
  (`broker.existingSecret`) with the key `broker-url`, passed to the app and
  the worker as `CELERY_BROKER_URL`, which takes precedence over `jobs.host`
  and `jobs.port`; an optional key `result-backend` is passed as
  `CELERY_RESULT_BACKEND`. For the bundled RabbitMQ, the Secret also has the
  keys `username` and `password` of its user, and the broker URL contains
  them (URL-encode reserved characters) and the host of the broker's
  Service, named like the app with the suffix `-broker` (see
  [Values](#values); set `fullnameOverride` to know it before installing,
  or check it with `helm template`). For an app `my-app` installed as
  release `my-app`:

    ```bash
    password="$(openssl rand -hex 16)"
    kubectl create secret generic my-app-celery \
        --from-literal=username=my-app \
        --from-literal=password="${password}" \
        --from-literal=broker-url="pyamqp://my-app:${password}@my-app-broker:5672//"
    ```

    The bundled RabbitMQ (a StatefulSet with one pod, which is replaced
    only once the old pod is gone) keeps its data in a
    PersistentVolumeClaim (`broker.persistence`: `size`, `accessModes`,
    `storageClass`, or an `existingClaim`), mounted at
    `/var/lib/rabbitmq/mnesia`, so queued tasks survive the replacement of
    its pod (e.g., on upgrades, except for the upgrade from foca-common
    0.1.0, see [Migrating to
    0.17.0](migration-0.17.md#broker-statefulset-and-persistence)): Celery's
    default queue is durable and its task messages are persistent. Results
    of the `rpc://` result backend (FOCA's default) are transient, though;
    set a persistent result backend (`result-backend`) if they matter. App
    charts need a template file with
    `foca-common.brokerPersistentVolumeClaim` (see the petstore example), or
    the broker's pod waits for its claim.

    RabbitMQ creates its user from the Secret only when it starts with
    empty data, so with persistence, changing the Secret does not change
    the user, and the old password stays valid. After changing the password
    in the Secret (in `password`, `broker-url` and, if it uses the broker,
    `result-backend`), change the user's, too, and roll the app's and the
    worker's pods (`rabbitmqctl` reads the password from standard input,
    so that it does not show up in process listings and audit logs):

    ```bash
    printf '%s' "${password}" | kubectl exec -i statefulset/my-app-broker -- \
        rabbitmqctl change_password my-app
    ```

    To change the user name, add the new user (here `my-app-2`) with access
    to the default virtual host, change the Secret (`username`, `password`,
    `broker-url` and, if it uses the broker, `result-backend`), roll the
    app's and the worker's pods, and then delete the old user:

    ```bash
    printf '%s' "${password}" | kubectl exec -i statefulset/my-app-broker -- \
        rabbitmqctl add_user my-app-2
    kubectl exec statefulset/my-app-broker -- \
        rabbitmqctl set_permissions -p / my-app-2 ".*" ".*" ".*"
    # change the Secret, roll the pods, then:
    kubectl exec statefulset/my-app-broker -- \
        rabbitmqctl delete_user my-app
    ```

    Without `broker.persistence.enabled`, the data is kept in the `emptyDir`
    with RabbitMQ's home (up to `broker.dataSizeLimit`) and lost with the
    pod, and each new pod creates the user from the Secret; values without
    a `broker.persistence` map (written for foca-common 0.1.0) disable
    persistence, too. For a highly available broker, use an external one:
    set only `broker.existingSecret` (and `worker.enabled`, if the release
    runs the worker).

    Celery declares transient non-exclusive queues, e.g., for the `rpc://`
    result backend (FOCA's default) and for remote control of the workers.
    RabbitMQ has deprecated them and denies them by default from 4.3 on, so
    the bundled RabbitMQ permits them in its config file (ConfigMap
    `<app name>-broker-config`); for an external RabbitMQ, set
    `deprecated_features.permit.transient_nonexcl_queues = true`, or the
    worker fails to start.
- **Network policies:** MongoDB's NetworkPolicy, enabled by default, admits
  only the app's pods of the release (and the worker's, if enabled); the
  broker's admits only the app's and the worker's pods. The app's
  NetworkPolicy is opt-in, as its peers depend on the cluster: set
  `<valuesKey>.networkPolicy.ingressFrom` to the pods of the ingress
  controller or Gateway (no defaults; see [NetworkPolicy
  peers](#networkpolicy-peers) for common setups). The kubelet's probes are
  always admitted.
- **OpenShift:** without an Ingress or HTTPRoute, a Route is created if the
  cluster serves `route.openshift.io/v1` (unless `<valuesKey>.route.enabled`
  is false); on clusters with
  `security.openshift.io/v1`, the user and group IDs are omitted from the
  security contexts, as OpenShift assigns them.
- **Gunicorn:** the `<valuesKey>.gunicorn` values are passed to the app's
  image as `GUNICORN_CMD_ARGS`, which take precedence over the settings of
  the image's command, e.g., FOCA's default settings
  (`--config python:foca.gunicorn_config`; see [Running in
  production](deployment.md#running-in-production) for the settings, why
  they are set, and how to override them); omit them if the image does not
  run Gunicorn. Options that the chart or FOCA rely on (`--bind`,
  `--preload`, `--graceful-timeout`) are rejected. As the root file system
  is read-only, start Gunicorn without a control socket: FOCA's settings
  disable it (as in the petstore example); otherwise, pass
  `--no-control-socket` in the image or via `extraArgs`, as Gunicorn 25.1
  or later logs a control server error at startup.

## Developing the library chart

The tests of the library chart are in `charts/foca-common/tests`; they render
the petstore chart with `helm template` and need [Helm][helm-install], the
version used in CI (see `.github/actions/test-chart`) for the snapshot
tests, as other versions may render whitespace or comments differently:

```bash
pytest charts/foca-common/tests
```

Snapshot tests compare the rendered output of a few sets of values with the
files in `charts/foca-common/tests/__snapshots__`. After intended changes of
the output, update them and review the diff:

```bash
UPDATE_SNAPSHOTS=1 pytest charts/foca-common/tests
git diff charts/foca-common/tests/__snapshots__
```

In CI, the petstore example is also installed with its thin chart on a
[kind](https://kind.sigs.k8s.io/) cluster with
[chart-testing](https://github.com/helm/chart-testing) (`ct install`),
which runs the chart's test (`templates/tests/`, `helm test`): it adds a
pet and reads it back, so that the app, its MongoDB and the app user are
checked. A second installation (`ci/celery-values.yaml`) adds the Celery
worker and the bundled broker; CI checks that the worker logs that it is
ready, i.e., connected to the broker, and that a task queued while no
worker runs survives a restart of the broker and then reaches it. A third one
(`ci/access-control-values.yaml`) enables access control with configured
policies, which FOCA stores on startup, so that the app user's access to the
access-control database is checked. A fourth one (`ci/gateway-values.yaml`)
exposes the app with an HTTPRoute on a Gateway of [Envoy
Gateway](https://gateway.envoyproxy.io/) (`.github/kind/gateway.yaml`) and
enables the app's NetworkPolicy; CI checks that HTTP is redirected to HTTPS,
that the app is reachable via HTTPS, and that the NetworkPolicy blocks other
pods.

### Releases

The library chart is versioned independently of FOCA, following [semantic
versioning](https://semver.org/): app charts depend on a particular version,
so every change of the library chart after a release needs a new
`version` in `charts/foca-common/Chart.yaml` (one for all changes up to the
next release); CI fails for changes of the chart (except its tests) since
its latest release (tag) that keep or lower the version. To release it,
merge the version change into `dev`, then create and push a signed tag
`chart-vX.Y.Z` of that version on the merge commit (only final versions are
released, no pre-releases):

```bash
git tag -s chart-v0.1.0 -m "foca-common 0.1.0"
git push origin chart-v0.1.0
```

The [release workflow][release-chart] runs the chart checks and the kind
installation of CI, checks that the tag is signed (with a signature that
GitHub verifies), is on `dev` and matches the chart's version, and that the
version has not been published yet; it then packages the chart, pushes it
to `oci://ghcr.io/elixir-cloud-aai/charts/foca-common`, and attests and
signs it (see [verifying images and
charts](deployment.md#verifying-images-and-charts)). Published versions
are never overwritten. If attesting or signing fails after the push, the
version stays published without them (a re-run stops at the version check);
release a new version. Tags cannot be deleted or moved (see below): if a
release fails, re-run its workflow for the same tag, which passes the
version check as long as the version has not been published; if the tagged
commit itself is wrong, fix it, bump the chart's version and release a new
tag. App charts then depend on the chart as shown in [Building an app
chart](#building-an-app-chart).

After the first release, an organization admin opens the package
`charts/foca-common` in the organization's GitHub package settings and:

- makes it public (new packages are private), so that app charts can pull it
  without credentials;
- connects it to the `foca` repository, or under "Manage Actions access"
  gives the repository the role "Write", so that later releases can push to
  it.

The organization may also need to allow members' Actions to create packages
for the first release. Anyone who may push a signed `chart-v*` tag can
release, so a tag ruleset of the repository restricts who may create
`chart-v*` and `v*` tags (admins only) and blocks updates and deletions of
these tags for everyone. To inspect a release, run:

```bash
helm show chart oci://ghcr.io/elixir-cloud-aai/charts/foca-common --version 0.1.0
```
